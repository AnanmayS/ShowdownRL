# Fix the Pipes Before Training Smarter Agents

ShowdownRL's win rate is not held back by PPO hyperparameters, network width or the choice between MaskablePPO and RecurrentPPO. Two things upstream of learning are holding it back. First, the live bot has been playing on corrupted inputs. It swaps its own Pokémon with the opponent's, reads PP counters as base power, sees empty type fields, and is never allowed to switch voluntarily. Second, the training simulator is a different game from Pokémon. The agent always moves first, and move type multipliers never update after a switch. On today's code, **every PPO checkpoint loses to a one-line "attack with the best power × accuracy × multiplier" heuristic in its own simulator (60–65% vs 70.8% in rich mode, 47–55% vs 66.2% in advanced mode)**. The published 79% benchmark reproduces at 66.9%. The roadmap therefore runs in three stages. In days: repair the live bridge (ideally by replacing DOM scraping with poke-env), deploy a correct damage-aware heuristic, and fix evaluation so improvements are visible at all. In weeks: move training onto the real Showdown simulator through poke-env in Gen 9 Random Battles, with damage-calc, speed and belief features, a BC warm start with a KL anchor, and a PFSP league. In months: add an entity-transformer policy and decision-time determinized search, the two ingredients behind every Random Battle bot above about 80% GXE. Progress should be measured on a fixed ladder of real-simulator opponents (RandomPlayer, MaxBasePowerPlayer, SimpleHeuristicsPlayer, local Foul Play) with confidence intervals. A few hundred public-ladder games then serve as the final check. Simulator win rate should stop being the headline number.

## The deployed bot has been playing on noise

The most important finding is that sim improvements from v11 through v24 could not have reached the live ladder even in principle. The live client does not use poke-env. It drives the play.pokemonshowdown.com website through Playwright and scrapes the DOM with injected JavaScript ([live.py:150-224](../showdownrl/live.py)). That scraper maps the left status bar to "active" and the right one to "opponent". The 17 saved debug snapshots show this is backwards. In a battle that opens "Go! Glimmora!", the agent's moves are Glimmora's set (Spikes, Stealth Rock, Earth Power, Sludge Wave), yet the bridge labels Cobalion as active. The battle log calls it "the opposing Cobalion" ([live.py:185-188](../showdownrl/live.py), [live.py:218-219](../showdownrl/live.py)). **Own HP and opponent HP, the first two observation features, are exchanged**, and the "finish" flags are computed against the agent's own health.

Move data is worse. The scraper reads `data-movetype`, `data-category` and `data-basepower` attributes that are empty in all 17 snapshots. Every Pokémon's type list is also empty ([live.py:189-196](../showdownrl/live.py)). The fallback parser takes the first 2–3 digit number in the button text as base power ([ai.py:115-130](../showdownrl/ai.py)). Button text looks like "Calm MindPsychic 32/32", so **Calm Mind is read as 32 base power and Draco Meteor (8/8 PP) as 0**. The heuristic fallback uses the same parser, so it is equally blind ([ai.py:177-189](../showdownrl/ai.py)). The behaviour matches the corruption. The v11 policy used Stealth Rock on consecutive turns while the log said "But it failed!", and in another battle it used Calm Mind eight turns running.

Action coverage is crippled as well. The live mask enables only move slots, so the policy can never choose a voluntary switch ([policy_bridge.py:358-363](../showdownrl/policy_bridge.py)). Forced switches are picked by a heuristic that sees empty types and null HP ([live.py:769-797](../showdownrl/live.py)). The switch list includes the Pokémon already on the field. Tera is never used. The bridge builds only 14-, 46- and 106-dimensional observations. The 86-dimensional advanced models (v23, v24) therefore throw on `predict`, and the bridge silently falls back to the corrupted heuristic ([policy_bridge.py:344-371](../showdownrl/policy_bridge.py)). Recurrent models are not supported live at all. As a result, the evidence for live strength is **six logged battles. Three PPO runs crashed at turn 0, two ended "unknown", and none record which model played.** The blog's claim that live PPO "consistently demonstrates competent play" has no data behind it ([blog:410](../docs/blog/showdownrl-technical-deep-dive.md)).

The fix is cheap relative to its impact, and there are two ways to do it. The narrow repair flips the bar mapping, excludes the active Pokémon from switch options, unmasks switches, and reads move type, category and power from the battle's `request` JSON or tooltips instead of button text. That last part rests on the assumption that the current client exposes them, which the audit could not verify. The better repair deletes the scraper. poke-env is actively maintained (0.16.1, August 2026). It ships a documented example for connecting to the public server and challenging humans, and it parses the Showdown protocol into typed battle objects with automatic action-mask tracking since 0.13.0 ([PyPI](https://pypi.org/pypi/poke-env/json), [poke-env releases](https://github.com/hsahovic/poke-env/releases), [poke-env examples](https://poke-env.readthedocs.io/en/latest/examples/index.html)). Moving the live client to poke-env also lets the same observation code serve training and deployment, which removes the whole class of mismatch bugs the audit found.

Until a retrained policy exists, the live bot should run a **correct damage-aware heuristic**, not any current PPO checkpoint. In the project's own simulator, that heuristic already beats every PPO model. On real Showdown, poke-env's SimpleHeuristicsPlayer is a meaningful benchmark: a small masked PPO agent on real PS reached only **31.1 ± 2.9%** against it ([PokeRL](https://github.com/Siddharth-Y26/PokeRL)).

## The simulator teaches a game that is not Pokémon

`SimplePokemonMoveEnv` is an abstract 4v4 duel. Moves are random (base power, accuracy, multiplier) tuples, damage is deterministic, and **the agent always moves first** ([simple_env.py:1093-1098](../showdownrl/simple_env.py)). The audit measured what that last rule is worth. It made the opponent move first and kept the same type-aware heuristic as the agent. **Win rate fell from 67.7% to 34.8% in rich mode and from 66.4% to 31.7% in advanced mode.** Move order alone decides roughly 33 points. A policy trained this way never has to reason about being outsped or knocked out before it acts, and that consideration dominates real Random Battles.

The second structural bug removes the core skill of competitive Pokémon, switching into a resist. Type multipliers for the active Pokémon and every bench Pokémon are computed once at reset against the opponent's lead. They are never recomputed after either side switches ([simple_env.py:728-739](../showdownrl/simple_env.py), [simple_env.py:951](../showdownrl/simple_env.py)). The audit forced an opponent switch in 300 seeds. The new opponent had a different typing in 297 of them, and **the agent's multipliers changed in 0 of 297**. The 18-dimensional bench type features therefore describe only the opponent's lead. This explains why the rich models switch just 1.4–6.7% of the time.

A long tail of smaller bugs also corrupts the learning signal:

- Accuracy is applied twice (roll to hit, then multiply damage by accuracy again), so expected damage scales with acc².
- Life Orb recoil lands on the wrong side.
- Opponent status moves in non-advanced modes lower both sides' attack.
- Agent status moves do nothing in rich mode.
- Stealth Rock scales with current HP, not max HP.
- Hazards skip faint replacements.
- Boosts and Choice lock survive switching.
- Sleep and freeze are never sampled ([simple_env.py:885-951](../showdownrl/simple_env.py), [simple_env.py:1018-1044](../showdownrl/simple_env.py), [simple_env.py:766-794](../showdownrl/simple_env.py)).

The observation omits both sides' types, attack boosts and the turn count. It encodes status, item and ability as ordinal integers, and it leaks the opponent's hidden item and ability ([simple_env.py:399-480](../showdownrl/simple_env.py)). The action mask hard-codes thresholds for when to heal, set up or use status moves ([simple_env.py:529-585](../showdownrl/simple_env.py)). What is left for the policy to learn is mostly "which attack", and the heuristic already answers that.

These facts explain the version history better than any optimisation story. The audit re-ran every compatible checkpoint on current code (500 episodes, fixed seeds, masks on). None of the post-v11 ideas beat v11: mixed opponents, 10M steps, LSTMs, advanced mechanics, self-play or BC fine-tuning. v24 (BC fine-tune) was the worst, at **46.6%** against type_aware in advanced mode, versus the heuristic's 66.2%. The advanced models switch 21–29% of the time and draw 13–17% of games, which suggests they found degenerate hazard or regenerator loops that the reward allows. The ceiling is the environment, not the learner.

The practical conclusion is to **stop investing in the custom simulator as the main training target**. It is still useful as a fast smoke-test and pretraining stage, but only after its two structural bugs are fixed. Move order should come from a speed stat with random ties, and multipliers should be recomputed on every switch. Fixing the remaining bugs is worthwhile only if the simulator stays in the pipeline. Its skills will not transfer to a 6v6 game with real sets, stats, speed tiers, priority, Tera, Protect and pivoting, none of which it models.

## Current evaluation cannot see a seven-point improvement

Before any change can be judged, measurement has to work, and today it does not:

- **Best-model selection is noise.** Training evaluations run 20 episodes and save the checkpoint with the best mean reward ([train_ppo.py:272-273](../scripts/train_ppo.py), [train_ppo.py:449-460](../scripts/train_ppo.py)). A 20-game win rate has a 95% confidence interval of roughly ±20 points, so the saved "best" checkpoints are mostly early-training noise. v24's "best" came from 300K steps, where per-eval mean reward peaked in a series ranging from −0.99 to 1.16. In the audit's runs, final checkpoints matched or beat the "best" ones.
- **The official evaluator can't handle the current models.** It accepts only toy, typed and rich mechanics, misreads 86-dim advanced models as rich, loads recurrent models without episode-start flags, and reports no confidence intervals ([evaluate_model.py:65-70](../scripts/evaluate_model.py), [evaluate_model.py:191-199](../scripts/evaluate_model.py)).
- **Nothing ties a model to its code.** Metadata stores no git SHA or environment version ([train_ppo.py:368-398](../scripts/train_ppo.py)), so removing reward shaping after v11 silently invalidated the published benchmark.

The literature is clear about how many games real improvements need. With a 50% baseline, two-sided α = 0.05 and 80% power, detecting a 5-point gain takes about 785 head-to-head games. A 3-point gain takes about 2,200, and a 2-point gain about 4,900. Comparing two agents through a common third opponent roughly doubles each figure. A 200-game evaluation has a ±6.9-point interval and cannot separate checkpoints that differ by less than about 7 points. Rigorous deep-RL evaluation reports interval estimates, not point estimates ([Agarwal et al. 2021](https://arxiv.org/abs/2108.13264)). Chess-engine testing uses sequential probability ratio tests to stop as soon as the evidence is conclusive ([Chessprogramming wiki](https://www.chessprogramming.org/Sequential_Probability_Ratio_Test)). Elo alone hides non-transitive cycles, and a Nash-based view of the cross-play matrix exposes them ([Balduzzi et al. 2018](https://arxiv.org/abs/1806.02643)).

Bot-versus-bot numbers also do not predict human results. RotomAI beat SimpleHeuristicsPlayer 73% of the time over 9,000 games and reached 0.74 GXE on an agent-only ladder. On the real human ladder it went 35–65, with 30% GXE. The author's diagnosis was that "the policy never saw the human metagame" ([RotomAI](https://github.com/BhaveshThapar/RotomAI)). Metamon likewise treats SimpleHeuristicsPlayer as useful only as an early-stage metric ([Metamon](https://github.com/UT-Austin-RPL/metamon)).

The measurement stack follows from this. Bulk evaluation runs on a local Showdown server started with `--no-security`, which removes throttling and login ([poke-env README](https://github.com/hsahovic/poke-env)). The opponents form a fixed ladder: RandomPlayer (a basic agent should reach about 95%), MaxBasePowerPlayer (about 60–70%), SimpleHeuristicsPlayer (about 30% is typical for a small agent, and beating it more than half the time is a real milestone), then Foul Play running locally ([PokeRL](https://github.com/Siddharth-Y26/PokeRL), [Foul Play](https://github.com/pmariglia/foul-play)). Where the simulator allows it, games should be seeded, and in "duplicate" style each team pairing is played twice with teams swapped. Promotion decisions use SPRT, and checkpoints are rated with a round-robin Bradley–Terry fit.

The public ladder is the final check and should be used sparingly. The PokéAgent Challenge required at least 250 games per agent for statistical validity ([PokéAgent](https://arxiv.org/html/2603.15563v1)), and Metamon's ladder evaluations used 400–800+ games per agent ([Metamon paper](https://arxiv.org/html/2504.04395)). Showdown's only relevant rule forbids gaming the ladder, for example by losing on purpose to yourself or a friend ([PS rules](https://pokemonshowdown.com/rules)). Play one account, one battle at a time, and never ladder two of your own bots against each other.

## Real-simulator training with the right features is the core bet

Gen 9 Random Battles is the right format to target. It is what the live bot already plays: the snapshots show Glimmora, Raging Bolt and Gholdengo. It needs no teambuilding, and its hidden information is unusually inferable. The pkmn randbats data is regenerated hourly from 100,000 simulated teams. It lists every species' level, EVs, roles, move pools, items, abilities and Tera types ([pkmn/randbats](https://github.com/pkmn/randbats), [data.pkmn.cc](https://data.pkmn.cc/randbats/gen9randombattle.json)). Because level and EVs are fixed, an opponent's exact stats and speed can be computed on sight. Foul Play credits its higher random-format ratings (88% GXE in Gen 9 RB versus 80% in Gen 9 OU) to exactly this "reliable information about the opponent's team" ([Foul Play blog](https://pmariglia.github.io/posts/foul-play/)). Jaxcalibur's author says the restricted format "significantly aided" its climb to #1 ([Smogon](https://www.smogon.com/forums/threads/jaxcalibur-a-gen-9-randbats-bot-that-reached-1-on-the-ladder.3787537/)).

The infrastructure is standard. Subclass poke-env's `SinglesEnv`, wrap it in `SingleAgentWrapper` and `Monitor`, and parallelise with `SubprocVecEnv`. This is the official SB3 recipe ([poke-env RL example](https://poke-env.readthedocs.io/en/latest/examples/reinforcement_learning.html)). Throughput is limited by websocket round-trips, not compute. A hobby benchmark found env workers at 13–17% CPU each and recommended 12–16 envs across two or more Showdown processes with `torch_threads=1`. RAM, not CPU, was the binding limit: 24 subprocesses used 15.4 GB ([PokeRL](https://github.com/Siddharth-Y26/PokeRL)). Expect tens to low hundreds of steps per second on a laptop, far slower than the custom env. That cost is worth paying because every win on this environment is a win on the real game. The existing SB3/MaskablePPO code carries over almost unchanged. The action space grows from 7 to the 13–14 actions used by Metamon and ps-ppo (four moves, five switches, and Tera variants of the four moves), and masks come from the env rather than hand-written thresholds ([Metamon](https://github.com/UT-Austin-RPL/metamon), [ps-ppo](https://github.com/Nebraskinator/ps-ppo)).

Features matter more than architecture at this scale. The official poke-env example uses only 12 features: base powers, type multipliers, and fainted and HP fractions ([poke-env RL example](https://poke-env.readthedocs.io/en/latest/examples/reinforcement_learning.html)). The highest-value additions, roughly in order, are:

1. Expected damage percentage for each of our moves against the opponent's active, and the opponent's worst-case damage against us. poke-env has had a built-in Gen 9 damage calculator since 0.10.0.
2. A "who moves first" flag that accounts for priority, Choice Scarf probability, paralysis and boosts.
3. Randbats-derived belief marginals over the opponent's role, moves, item and Tera type, filtered as information is revealed.
4. Matchup scores for each bench switch-in.
5. One-hot types and statuses, boost stages, and hazards and screens on each side.

Hand-computed matchup features inject domain knowledge a network would otherwise need millions of games to learn. Explicit belief features also let a feed-forward MaskablePPO compete without recurrence. This matters because the project's LSTM runs never beat the MLP, and recurrent PPO is easy to break silently: hidden states need resets on episode boundaries and sequential minibatches ([37 PPO implementation details](https://iclr-blog-track.github.io/2022/03/25/ppo-implementation-details/)).

Four training-side changes go with the migration. First, **warm-start with behaviour cloning from a stronger teacher**, not from the agent's own rollouts. The current BC pipeline distils v23 into itself, so it can at most copy v23. It also has a weight-transfer bug that silently skips every hidden-layer bias ([behavior_clone.py:180-213](../scripts/behavior_clone.py), [collect_expert_data.py:60-65](../scripts/collect_expert_data.py)). ps-ppo warm-started from SimpleHeuristicsPlayer before PPO ([ps-ppo](https://github.com/Nebraskinator/ps-ppo)). In VGC-Bench, BC-initialised self-play ranked first at every team-set size ([VGC-Bench](https://arxiv.org/html/2506.10326)).

Second, **anchor PPO fine-tuning with an annealed KL penalty toward the frozen BC policy**. VPT found this KL term crucial: without it, agents forgot skills learned in pretraining ([Baker et al. 2022](https://arxiv.org/pdf/2206.11795)). Omitting it is the likely reason v24's fine-tune fell below both its teacher and its own clone. In SB3 this is about 50–100 lines in a `MaskablePPO.train()` subclass.

Third, **make win/loss the dominant reward and use only potential-based shaping**. Shaping of the form γΦ(s′) − Φ(s), with Φ built from HP and faint differentials, provably leaves the optimal policy unchanged ([Ng, Harada & Russell 1999](https://people.eecs.berkeley.edu/~russell/papers/icml99-shaping.pdf)). The current per-turn HP-delta reward invites the stalling and loops the advanced models appear to have found.

Fourth, **retune PPO toward documented defaults**. Use much larger rollouts (16k–64k steps per update, not 2,048), GAE λ around 0.9–0.95, no value-loss clipping, observation normalisation, and a learning rate around 3e-4 ([Andrychowicz et al. 2020](https://arxiv.org/abs/2006.05990)). Also stop sweeping widths and timesteps. The audit shows 10M steps and 512-wide networks bought nothing on the old env.

**Replace the self-play league as well.** Today's opponent swaps between a league model and a scripted bot on each action inside the same game, which makes it incoherent. The pool is ten 78-dimensional checkpoints from a 450K-step window of one run, and none of them loads in the current env ([train_ppo.py:102-126](../scripts/train_ppo.py)). The low-cost replacement is AlphaStar-style prioritised fictitious self-play, with opponents fixed for a whole game and weighted by (1 − win rate)^p so the agent trains most against opponents it struggles with ([Vinyals et al. 2019](https://www.nature.com/articles/s41586-019-1724-z), [mini-AlphaStar](https://arxiv.org/pdf/2104.06890)). Add three safeguards. Keep fixed scripted anchors in the pool to catch regressions. Admit a new snapshot only if it beats the pool. Train an occasional short-lived exploiter against the frozen main agent to surface blind spots. Keep expectations modest: VGC-Bench found all its agents "approximately 100% exploitable" by a BC-initialised exploiter ([VGC-Bench](https://arxiv.org/html/2506.10326)). Metamon found that naive self-play data made agents overfit to themselves until they added large volumes of diverse synthetic data ([Metamon paper](https://arxiv.org/html/2504.04395)).

## Search and relational networks separate 72% GXE from 95%

Once the agent trains on the real game, the evidence points to two larger investments, and both are proven in this exact format. The first is architecture. ps-ppo's PokeTransformer has 15 tokens: one per Pokémon plus field, actor and critic tokens. It uses identity embeddings for species, moves and abilities, and a 51-bin distributional value head. It reached **1900+ Elo in Gen 9 Random Battles and above 85% against SimpleHeuristicsPlayer with no search**, after 2 days of Ray-distributed PPO on one RTX 3090. A replication of an MLP baseline with the same PPO hyperparameters plateaued at **about 1100 Elo** ([ps-ppo](https://github.com/Nebraskinator/ps-ppo)).

That roughly 800-point gap is the strongest single-author evidence that relational modelling matters. Metamon (two-hot value classification over a causal transformer) and VGC-Bench (entity encoders with masked logits) use the same design ([Metamon paper](https://arxiv.org/html/2504.04395), [VGC-Bench](https://arxiv.org/html/2506.10326)). Cross-entropy value losses such as two-hot or HL-Gauss also scale better than MSE regression ([Farebrother et al. 2024](https://arxiv.org/abs/2403.03950)). There is counter-evidence: a 2026 small-budget Gin Rummy study found learned embeddings and extra capacity did little to break its ceiling ([arXiv 2607.06854](https://arxiv.org/abs/2607.06854)). Treat the transformer as a bet that pays off with volume. Build it after the feature-rich MLP has plateaued on the real simulator, not before.

The second investment is decision-time search, the clearest separator in the Random Battle literature:

| Agent | Approach | Result |
|---|---|---|
| Huang & Lee | Search-free PPO self-play | 72% GXE in Gen 7 RB |
| Wang | Same kind of PPO actor-critic plus MCTS | 79.5% GXE, #8 on the Gen 4 RB ladder |
| Laplace | MCTS over 8 sampled opponent teams per turn | 83.3 GXE in Gen 9 RB |
| Foul Play | MCTS with DUCT over determinised sets on the Rust poke-engine | 88% GXE in Gen 9 RB |
| Jaxcalibur | AlphaZero-style self-play network plus pUCT search | #1 on the Gen 9 RB ladder, 95.3 GXE |

Sources: Huang & Lee and Wang as summarised by Metamon ([Metamon](https://arxiv.org/html/2504.04395v1), [MIT DSpace](https://dspace.mit.edu/handle/1721.1/153888)); [Laplace](https://www.trylaplaceai.com/); [Foul Play blog](https://pmariglia.github.io/posts/foul-play/); [Jaxcalibur on Smogon](https://www.smogon.com/forums/threads/jaxcalibur-a-gen-9-randbats-bot-that-reached-1-on-the-ladder.3787537/).

PokaiTrainer reached the same conclusion in VGC doubles: "the policy network alone loses to shallow heuristic search" ([PokaiTrainer](https://arxiv.org/html/2608.29197)). Foul Play's author ranks set prediction "as important as" search ([Foul Play blog](https://pmariglia.github.io/posts/foul-play/)). That is why the randbats belief features above are a prerequisite, not a nice-to-have.

A feasible version for ShowdownRL has four steps:

1. Sample 4–16 opponent completions from the randbats belief state.
2. On each sample, run a 1–2 turn lookahead with DUCT at the simultaneous-move node, using the PPO policy as a prior and the PPO value head at the leaves.
3. Aggregate visit counts across samples.
4. Distil the search policy back into the network with an expert-iteration cross-entropy loss ([Anthony et al. 2017](https://arxiv.org/abs/1705.08439)).

The bottleneck is a fast, cloneable simulator. poke-engine does 25,000 MCTS iterations in 100 ms and has Python bindings (PyPI 0.0.48, July 2026) ([poke-engine](https://github.com/pmariglia/poke-engine), [PyPI](https://pypi.org/pypi/poke-engine/json)). Showdown's clock caps thinking time, and PokéChamp lost about a third of its games on time with an LLM in the loop ([PokéChamp](https://arxiv.org/html/2503.04094v1)). One open question needs checking before committing. The poke-engine README describes Gens 4–8 via feature flags, yet Foul Play plays Gen 9 Random Battles on it. Confirm Gen 9 and Tera coverage in the Python bindings first.

Human-replay offline RL, the method behind Metamon's #1 Gen 1 OU agent, is powerful but is **the wrong bet for Random Battles**. Metamon's 5.3M parsed trajectories cover Gen 1–4 OU tiers and Gen 9 OU, not Gen 9 Random Battles ([Metamon README](https://github.com/UT-Austin-RPL/metamon)). The same applies to its checkpoints as league opponents or evaluation baselines. If the project ever pivots to Gen 1 or Gen 9 OU, the calculus flips: advantage-filtered BC on Metamon data, plus Metamon checkpoints as opponents and baselines, becomes the highest-leverage path. For randbats, the stronger teacher has to be SimpleHeuristicsPlayer, a locally run Foul Play queried DAgger-style, or the agent's own search.

Work the table top to bottom. Phase 0 changes what the bot actually does on the ladder this week. It also makes every later number trustworthy, and no amount of training fixes an agent that thinks its opponent's HP is its own. Phase 1 changes the game being learned. The two things that did not work in the past are more timesteps and bigger networks on the wrong env, and that record argues against starting Phase 2 before Phase 1 shows real-simulator progress. Phases 2 and 3 are where the literature's large gains live. Their costs are real: weeks of engineering, a simulator integration whose Gen 9 coverage must be verified, and a turn timer that punishes slow search.

## Conclusion

Nearly all of the project's effort has gone into the learner. It has been two steps removed from the thing being measured, because a bridge fed the policy the wrong game state and a simulator taught it the wrong game. The encouraging corollary is that the first large gains are engineering, not research: a correct observation pipeline, the real simulator, and honest statistics. Each is cheaper than another 10M-step run and more likely to move the live win rate. A useful rule going forward: no change counts as an improvement until it survives a confidence interval on the real simulator against opponents it never trained on.

The research frontier also suggests a sharper strategic target than "a better PPO". In Gen 9 Random Battles, every agent above about 80% GXE pairs a learned network with explicit set inference and search. Pure policy networks, even good transformers, top out lower, and bot-versus-bot win rates overstate human-ladder strength. A realistic long-term goal for this project is a feature-rich, BC-anchored policy that clears 50% against SimpleHeuristicsPlayer on real Showdown. That policy would then serve as the prior and value function for a shallow determinized search. That is the Jaxcalibur recipe at hobby scale, and it is where the remaining win rate is.
